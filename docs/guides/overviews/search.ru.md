# Поиск: как работает гибридный поиск

**Аудитория:** разработчики, архитекторы, технические специалисты и продуктовые команды, которым необходимо понимать, как Synanton преобразует вопрос пользователя в авторизованный результат поиска.

**Уровень:** от концептуального до среднего

**Предварительные требования:** отсутствуют. Знание Query DSL, gRPC или математических методов ранжирования не требуется.

## Кратко

Synanton использует **гибридный поиск**, поскольку вопросы в корпоративной среде редко являются исключительно текстовыми.

Один запрос может одновременно требовать:

- поиска точных терминов;
- семантического поиска по смыслу;
- поиска связанных сущностей и отношений;
- проверки полномочий;
- дополнительного переранжирования результатов.

Поэтому Synanton рассматривает поиск как координированный процесс извлечения знаний, а не как один алгоритм поиска.

```text
Запрос
  │
  ├── Лексический поиск
  │
  ├── Семантический поиск
  │
  └── Поиск отношений
          │
          ▼
    Объединение результатов
          │
          ▼
    Расширение графом
          │
          ▼
      Переранжирование
          │
          ▼
Представление, разрешённое
     для данного субъекта
          │
          ▼
       Результаты
```

Конкретный путь выполнения зависит от запроса и доступных возможностей конкретного развёртывания.

---

# Какую задачу решает поиск

Корпоративные знания одновременно содержат несколько типов информации:

- точные идентификаторы и термины;
- понятия, сформулированные разными словами;
- отношения между сущностями;
- структурированные аннотации;
- классификацию безопасности;
- представления контента, которые могут отличаться для разных субъектов доступа.

Ни один отдельный механизм поиска не является одинаково эффективным для всех этих случаев.

Например:

> **Какие поставщики имеют контракты, срок действия которых скоро заканчивается, и каковы условия расторжения?**

Такой запрос фактически содержит несколько задач:

1. определить поставщиков и связанные с ними контракты;
2. найти контракты, приближающиеся к окончанию срока действия;
3. найти соответствующие условия расторжения;
4. найти условия, описывающие расторжение, даже если слово «расторжение» в них не используется;
5. учитывать полномочия текущего субъекта доступа.

Гибридный поиск позволяет выполнить эти задачи совместно.

---

# Почему Synanton использует несколько стратегий поиска

Каждая стратегия имеет собственную область эффективности.

| Стратегия | Хорошо работает для | Ограничение |
|---|---|---|
| **Лексический поиск** | Точные термины, имена, идентификаторы, доменная терминология | Не понимает смысловые перефразирования сам по себе |
| **Семантический поиск** | Смысл, синонимы, перефразирование, концептуальное сходство | Может недооценить редкий точный идентификатор |
| **Поиск по графу** | Отношения, владение, зависимости, связи | Не является механизмом текстового ранжирования |

Эти стратегии дополняют друг друга, а не являются взаимозаменяемыми.

Например, запрос:

> «условия прекращения соглашения»

может потребовать найти фрагмент:

> «каждая из сторон вправе расторгнуть настоящий договор»

несмотря на различие формулировок.

Одновременно запрос с номером договора или идентификатором поставщика требует точного лексического совпадения.

Поиск по графу добавляет другой тип контекста:

> Какой поставщик связан с этим договором?

Это уже вопрос об отношении между сущностями, а не только о текстовой релевантности.

# Как работает гибридный поиск

## 1. Запрос

Клиент отправляет поисковый запрос.

Запрос может содержать:

- естественный язык;
- точные термины;
- идентификаторы;
- фильтры;
- ограничения по отношениям;
- комбинации перечисленного.

Поисковая система определяет, какие механизмы извлечения релевантны данному запросу.

---

## 2. Лексический поиск

Лексический поиск сопоставляет термины запроса с индексированными терминами.

Текущая реализация использует **Synquest** как ядро лексического поиска.

Лексический поиск особенно эффективен для:

- имён;
- идентификаторов;
- кодов продукции;
- номеров договоров;
- точной доменной терминологии;
- редких терминов.

Он обеспечивает высокую точность, когда пользователь знает терминологию исходного контента.

Однако лексический поиск сам по себе не понимает, что:

> «расторгнуть соглашение»

и

> «прекратить действие договора»

могут выражать одно и то же понятие.

---

## 3. Семантический поиск

Семантический поиск сопоставляет **смысл**, а не только совпадение слов.

Контент представляется вектором, а запрос представляется в том же семантическом пространстве. Поиск затем определяет контент, находящийся достаточно близко к запросу по смыслу.

Например:

> «условия прекращения соглашения»

может найти:

> «каждая из сторон вправе расторгнуть настоящий договор»

даже при минимальном лексическом пересечении.

Семантический поиск дополняет лексический, а не заменяет его.

---

## 4. Поиск по отношениям

Поиск по отношениям работает со знаниями о сущностях и связях между ними.

В текущей архитектуре для графовой части используется **Relix**.

Например:

```text
Поставщик
   │
   ├── поставляет → Продукт
   │
   ├── имеет → Договор
   │
   └── регулируется → Политика
```

Графовый поиск позволяет отвечать на вопросы:

- Какие договоры принадлежат этому поставщику?
- Какая политика регулирует данный договор?
- Какие клиенты затронуты инцидентом?
- Какие обязательства зависят от данного соглашения?

Графовый поиск решает другой класс задач, чем текстовая релевантность.

---

# Объединение результатов

Лексический и семантический поиск формируют независимо ранжированные списки кандидатов.

Их оценки нельзя напрямую считать сопоставимыми: лексическая оценка релевантности и векторная оценка сходства представляют разные величины.

Поэтому Synanton объединяет **позиции в ранжированных списках**, а не пытается складывать исходные оценки.

В текущей архитектуре для этого используется **Reciprocal Rank Fusion (RRF)**.

Концептуально:

```text
Лексические результаты       Семантические результаты
         │                            │
         └────────────┬───────────────┘
                      ▼
              Ранговое объединение
                      │
                      ▼
              Единый набор кандидатов
```

Кандидат, который занимает высокую позицию в нескольких независимых результатах поиска, получает более сильное совокупное свидетельство релевантности, чем кандидат, который оказался первым только в одном списке.

---

# Расширение контекста через граф

Графовый поиск может применяться после формирования начального набора текстовых кандидатов.

Например:

```text
Фрагмент договора
      │
      ▼
   Поставщик
      │
      ▼
Дополнительное соглашение
      │
      ▼
Обновлённые условия штрафов
```

Так поиск может связывать сведения, распределённые между разными документами.

Граф в этом случае предоставляет **контекст отношений**, а не просто выступает ещё одним текстовым механизмом ранжирования.

---

# Переранжирование

Некоторые запросы выигрывают от дополнительного этапа ранжирования.

После формирования и объединения кандидатов необязательный reranker может повторно оценить наиболее перспективные результаты относительно полного запроса.

```text
Первичное извлечение
       ↓
Набор кандидатов
       ↓
Объединение / расширение
       ↓
Reranker
       ↓
Итоговое ранжирование
```

Переранжирование дороже первичного поиска, поэтому оно обычно применяется только к ограниченному числу кандидатов.

Если reranker недоступен, поиск может вернуть результаты после объединения без этого этапа. Если API предоставляет информацию о режиме выполнения, состояние деградации должно быть явно отражено в результате.

**Доступность и качество ранжирования — разные характеристики:** отказ необязательного этапа ранжирования не должен автоматически делать весь поиск недоступным.

---

# Безопасность является частью поиска

Результаты поиска должны оцениваться с учётом субъекта, выполняющего запрос.

Авторизация поэтому не должна рассматриваться только как финальный фильтр отображения.

Концептуально:

```text
Запрос
  │
  ▼
Авторизованное пространство кандидатов
  │
  ├── лексический поиск
  ├── семантический поиск
  └── графовый поиск
          │
          ▼
       Объединение
          │
          ▼
       Переранжирование
          │
          ▼
Представление, разрешённое субъекту
```

Точная граница и механизм выполнения определяются архитектурой **Security** и **Security-Aware Search**.

Ключевое свойство:

> Неавторизованная информация не должна становиться обычным кандидатом поиска только для того, чтобы быть удалённой после ранжирования.

Это также важно для предотвращения косвенного раскрытия через:

- количество результатов;
- статистику ранжирования;
- подсказки;
- фрагменты текста;
- подсветку терминов;
- другие поисковые метаданные.

Подробная модель описана в руководстве **Security: Classification, Masking, and Authorization**.

---

# Один запрос может давать разные представления

Два субъекта могут выполнить один и тот же запрос и получить разные представления одного и того же знания.

Например:

```text
Субъект A
  → имеет доступ к FINANCIAL
  → «Валовой доход: €180 000»

Субъект B
  → не имеет доступа к исходному значению FINANCIAL
  → «Валовой доход: [REDACTED:FINANCIAL]»
```

Это отличается от полного сокрытия результата.

Знание остаётся полезным, а представление соответствует полномочиям субъекта.

---

# Пример

Пусть пользователь спрашивает:

> **Какие обязательства возникают, если поставщик нарушает срок поставки?**

### Лексический поиск

Находит фрагменты, содержащие:

- поставщик;
- поставка;
- срок;
- задержка.

Например:

> «Поставщик обязан уведомить покупателя в течение 48 часов о предполагаемой задержке».

### Семантический поиск

Может найти:

> «В случае нарушения согласованного графика поставки применяются следующие меры ответственности».

Хотя слово «срок» в исходном запросе и фрагменте отсутствует, смысловая связь сохраняется.

### Графовый поиск

Из сущности поставщика может быть найдено связанное знание:

```text
Поставщик
  │
  ├── Договор
  │
  └── Дополнительное соглашение
        │
        └── Изменённые условия штрафов
```

Дополнительное соглашение может содержать более позднее изменение обязательств.

### Объединение и переранжирование

Текстовые кандидаты объединяются, графовый контекст добавляется там, где он релевантен, а наиболее важные кандидаты могут быть повторно ранжированы относительно полного вопроса.

### Безопасность

В результат попадают только те знания и представления, которые доступны конкретному субъекту.

Поэтому итог может объединять:

- точные положения договора;
- семантически связанные положения;
- связанные договорные факты;

не нарушая модель авторизации.

---

# Поиск по нескольким языкам

Корпоративные знания редко ограничиваются одним языком.

Лексический и семантический поиск решают проблему многоязычности разными способами.

Для языков, где стандартное разделение по пробелам неприменимо, лексический слой может использовать соответствующую языку стратегию индексирования вместо предположения, что каждое слово отделяется пробелом.

Семантический поиск предоставляет дополнительный механизм: embedding-модель может представлять смысл текста независимо от точной языковой формулировки в пределах поддерживаемых языков.

Таким образом, многоязычный поиск не требует от пользователя знать точную формулировку исходного документа.

Детали языково-зависимой реализации относятся к документации **Search Architecture**.

---

# Производительность и ограничение ресурсов

Поиск должен оставаться предсказуемым при совместной работе с корпоративными нагрузками.

Архитектура поэтому ограничивает объём работы на нескольких этапах.

Примеры:

- ограниченный размер набора кандидатов;
- переранжирование только верхней части кандидатов;
- ограничения ресурсов семантического поиска;
- безопасное кэширование результатов;
- бюджеты выполнения запросов.

Кэш не должен приводить к тому, что один субъект получает представление, предназначенное для другого субъекта.

Ограничения ресурсов также должны быть наблюдаемыми, а не скрыто менять смысл результата.

Численные показатели производительности следует интерпретировать как **целевые значения или измерения в определённых условиях**, а не как безусловные гарантии.

---

# Деградированный режим

Поиск должен различать:

1. полноценное выполнение;
2. успешное выполнение с ограниченной функциональностью;
3. недоступность выполнения.

Например, если сервис семантического поиска временно недоступен, платформа может продолжить работу с оставшимися механизмами.

Если деградированный режим существенно влияет на поведение поиска, состояние выполнения должно быть отражено в соответствующем контракте.

Результат в деградированном режиме не должен молча выглядеть полностью эквивалентным результату полноценного выполнения, если это различие важно для эксплуатации.

---

# Что может изменить результаты поиска?

Результаты могут измениться при изменении:

- исходного контента;
- семантических чанков;
- аннотаций;
- отношений;
- поисковых индексов;
- embeddings;
- классификации безопасности;
- полномочий;
- конфигурации поиска;
- моделей ранжирования.

Не каждое изменение требует одинакового объёма пересчёта.

Например:

```text
Изменение полномочий
      ↓
Изменение видимости при запросе
      ↓
Переработка контента не требуется
```

В отличие от:

```text
Изменение правила классификации
      ↓
Затронут существующий контент
      ↓
Переклассификация / пересчёт
      ↓
Обновление поисковых проекций
```

Архитектура Recalculation определяет зависимости и модель выполнения пересчёта.

---

# Что остаётся стабильным?

Даже при изменении конкретных технологий следующие архитектурные границы должны сохраняться:

- поиск работает поверх канонической модели знаний и её проекций;
- лексический, семантический и графовый поиск остаются различными возможностями;
- результаты извлечения объединяются явным механизмом fusion;
- дорогостоящие этапы работают с ограниченным набором кандидатов;
- безопасность определяет доступное субъекту знание и его представление;
- производное поисковое состояние может быть восстановлено из авторитетного состояния.

Реализация конкретного поискового движка или хранилища может изменяться без изменения этих архитектурных контрактов.

# Часто задаваемые вопросы

### Заменяет ли семантический поиск лексический?

Нет.

Семантический поиск хорошо работает со смыслом и перефразированием. Лексический поиск остаётся важным для точных идентификаторов, имён, кодов и доменной терминологии.

### Заменяет ли графовый поиск обычный поиск?

Нет.

Графовый поиск отвечает на вопросы об отношениях. Он дополняет текстовый поиск.

### Почему нельзя напрямую сравнивать лексические и векторные оценки?

Потому что они имеют разный смысл и разные шкалы. Ранговое объединение позволяет не считать эти оценки одной и той же измеримой величиной.

### Всегда ли более широкая роль получает больше результатов?

Не обязательно.

Чанки, содержащие только несекретную информацию, могут выглядеть одинаково для разных субъектов. Более широкие полномочия могут дать доступ к более полному представлению уже найденного результата, а не обязательно к дополнительным документам.

Дополнительные документы появляются, если различаются права доступа к самим ресурсам.

### Что происходит, если reranker недоступен?

Поиск может вернуть результаты после fusion без необязательного этапа переранжирования. Если это влияет на режим выполнения, соответствующее состояние должно быть отражено в контракте.

### Может ли поисковый результат кэшироваться?

Да, если кэширование совместимо с требованиями авторизации и актуальности.

Результаты, зависящие от полномочий, не должны пересекать границы доступа.

# Итог

Поиск Synanton является **гибридным, потому что корпоративное знание неоднородно**.

Лексический поиск работает с точными терминами.

Семантический поиск работает со смыслом.

Графовый поиск работает с отношениями.

Fusion объединяет свидетельства из разных механизмов извлечения.

Reranking может улучшить порядок ограниченного набора кандидатов.

Безопасность определяет, какое знание и какое его представление доступно субъекту.

Recalculation поддерживает согласованность производного поискового состояния при изменении авторитетного знания.

В результате поиск является не просто расширенным полнотекстовым поиском, а поисковым слоем поверх **структурированной, связанной и защищённой модели знаний Synanton**.
