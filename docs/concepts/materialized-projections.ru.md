# Материализованные проекции в архитектуре знаний, ориентированной на ИИ (AI-Native)

## Аннотация

Корпоративные ИИ-системы обычно рассматривают знания как совокупность документов, фрагментов (чанков), эмбеддингов, узлов графа или поисковых индексов.

Synanton использует иную модель:

> **Корпоративные знания - это версионированный набор материализованных семантических проекций, созданных на основе разнородных исходных хранилищ, связанных информацией о происхождении (provenance), регулируемых контрактами формирования (derivation contracts) и ограниченных политиками безопасности.**

Материализованная проекция - это производное представление исходных знаний, оптимизированное для конкретной цели: лексического или семантического поиска, структурной навигации, разрешения сущностей, обхода графа, аналитики или иных вычислений.

Такая проекция **не является альтернативным источником истины**. Это производное состояние, корректность которого зависит от:

- версий исходных данных, на основе которых она была создана;
- процесса преобразования или модуля обработки, создавшего её;
- использованной онтологии и семантической конфигурации;
- конфигурации, примененной в процессе формирования;
- политики безопасности, действовавшей в момент материализации.

Эта модель возникла из практической инженерной задачи: проверки согласованности между хранилищем FileNET и индексом Lucene. Исходная задача требовала большего, чем просто сравнение двух хранилищ данных, поскольку объекты в них представляли собой намеренно различающиеся формы представления информации.

Это привело к формулировке более общей абстракции:

```text
Исходное хранилище
      │
      │ формирование (derivation)
      ▼
Материализованная проекция
      │
      ├── происхождение (provenance)
      ├── версия
      ├── безопасность
      └── подпись формирования
```

Та же абстракция применима к следующим преобразованиям:

```text
документы             -> фрагменты (чанки)
документы             -> лексический индекс
документы             -> эмбеддинги
документы             -> сущности
документы             -> граф
документы             -> краткие изложения (summary)
сущности              -> аналитические проекции
несколько источников  -> бизнес-объекты
несколько источников  -> поисковые проекции
```

Полученную архитектуру можно рассматривать как **систему инкрементальной сборки корпоративных знаний**.

------

# 1. Основная проблема

Традиционная архитектура поиска для ИИ часто представляется следующим образом:

```text
  Документы
       │
       ▼
Фрагменты (чанки)
       │
       ▼
Эмбеддинги
       │
       ▼
Векторный поиск
       │
       ▼
LLM (большая языковая модель)
```

Эта модель полезна как шаблон реализации, но она скрывает важное архитектурное свойство:

> Фрагменты, эмбеддинги, индексы, графы и сгенерированные факты являются производными представлениями эталонных данных.

Следовательно, они обладают семантикой жизненного цикла.

При изменении исходных знаний система должна определить:

1. какие производные объекты зависят от измененного источника; 2. какие производные объекты остаются валидными;
3. какие объекты необходимо признать недействительными;
4. какие объекты можно перестроить инкрементально;
5. сохраняются ли гарантии безопасности;
6. по-прежнему ли результирующие проекции удовлетворяют своим контрактам формирования.

Таким образом, задача состоит не просто в том, чтобы ответить на вопрос:

> «Как искать документы?»

Вопрос звучит так:

> **Как поддерживать достоверные материализованные представления развивающихся корпоративных знаний?**

------

# 2. От проверки соответствия FileNET и Lucene к общей модели

## 2.1 Исходная задача

Первоначальная задача проверки согласованности формулировалась так:

```text
Документ FileNET  vs  Документ Lucene
```

Прямое сравнение здесь недостаточно, поскольку эти два объекта имеют разные представления.

Объект FileNET может содержать:

```text
метаданные документа
бинарное содержимое
метаданные безопасности
информацию о версиях
```

в то время как представление в Lucene может включать:

```text
индексируемые поля
сохраняемые поля
токенизированные термины
векторы терминов
внутренние метаданные индекса
```

Некоторые исходные данные могут намеренно отсутствовать в проекции (например, содержимое документа может быть проиндексировано, но не сохранено в документе индекса и, как следствие, быть недоступным для сравнения).

Следовательно, условие:

```text
SourceObject == ProjectionObject
```

не является ни обязательным, ни желательным.

Суть вопроса заключается в следующем:

> **Является ли данная проекция корректной реализацией ожидаемого состояния источника в соответствии с предполагаемым правилом преобразования?**

------

# 3. Абстракция репозитория

Таким образом, компонент проверки согласованности может работать с минимальной абстракцией репозитория.

Концептуально:

```text
Repository<T>
scanIds(pageToken) -> Page<ID>,nextToken

fetch(id) -> Object<T>
```

Репозиторий предоставляет доступ к объектам, не требуя от проверяющего компонента знаний о своей физической реализации.

Репозиторием может выступать:

```text
FileNET
SharePoint
PostgreSQL
объектное хранилище
хранилище на базе Kafka
Lucene
Solr
Elasticsearch
векторное хранилище
графовое хранилище
хранилище чанков (фрагментов)
```

Компонент проверки не должен зависеть от того, чем является базовая реализация: базой данных, поисковой системой, объектным хранилищем или иной системой.

Его зона ответственности - логический набор данных.

------

# 4. Материализованная проекция

**Материализованная проекция** - это персистентное (постоянно хранимое) представление, полученное на основе одного или нескольких исходных артефактов.

Формально:

```text
P = T(S, O, C)
```

где:

- `S` = исходное состояние;
- `O` = онтология / семантическая модель;
- `C` = конфигурация преобразования;
- `T` = версионируемое преобразование или процессор;
- `P` = материализованная проекция.

Примеры:

```text
Документ
│
├── лексический процессор ──> Инвертированный индекс
├── процессор разбиения ───> Хранилище чанков
├── процессор эмбеддингов ─> Векторное хранилище
├── процессор сущностей ───> Хранилище сущностей
└── графовый процессор ────> Графовое хранилище
```

Проекция называется материализованной, поскольку ее производное состояние сохраняется независимо от источника, и к нему можно обращаться (выполнять запросы) или использовать его без повторного вычисления всего процесса преобразования.

------

# 5. Проекция не является источником истины

Проекция может содержать информацию, которой нет в исходных данных в точно таком же виде.

Например:

```text
   Документ
       │
       ▼
извлечение сущностей
       │
       ▼
Person("John Smith")
```

или:

```text
    Документ A - CompanyRevenue = $100M
    Документ B - CompanyRevenue = $200M
    Документ C - CompanyRevenue = $300M
       │
       ▼
    агрегация
       │
       ▼
CompanyRevenue = $600M
```

Проекция полезна именно тем, что представляет исходные данные в виде, оптимизированном для выполнения другой операции.

Однако:

> **Проекция не становится авторитетным источником данных лишь на том основании, что она материализована.**

Следовательно, исходные данные и проекция играют разные роли:

```text
Источник = авторитетное состояние

Проекция = производное материализованное состояние
```

Это различие является фундаментальным для Synanton.

------

# 6. Процесс получения проекции (деривация) - это не всегда функция

Распространенным упрощением является запись:

```text
P = T(S)
```

Однако связь между источником и проекцией не обязательно является взаимно-однозначной.

Один источник может порождать множество объектов-проекций:

```text
Документ A
    │
    ├── Фрагмент X
    ├── Фрагмент Y
    ├── Фрагмент Z
    └── Эмбеддинг E
```

И наоборот, проекция может зависеть от нескольких источников:

```text
Документ A ─────┐
Документ B ─────┼──> Фрагмент X
Документ C ─────┘
```

Или:

```text
FileNET ─────┐
DB1 ─────────┼──> Бизнес-объект ───> Поисковая проекция
DB2 ─────────┘
```

Поэтому общая связь выглядит так:

```text
Деривация ⊆ Источники × Проекции
```

и может включать зависимости типа «многие-ко-многим».

Для агрегированных проекций или проекций, зависящих от нескольких источников, зависимость естественнее представлять как набор зависимостей или гиперребро:

```text
{S1, S2, S3} ──> P
```

------

# 7. Необратимость проекции

Материализованные проекции часто приводят к потере информации.

Предположим:

```text
D1 = "Джон работает в ACME"
D2 = "Джон работает в ACME"
```

и обе они дают результат:

```text
P = "Джон работает в ACME"
```

Тогда:

```text
T(D1) = T(D2)
```

в то время как:

```text
D1 ≠ D2
```

Следовательно, обратная функция:

```text
T⁻¹(P)
```

не может однозначно восстановить исходный объект.

Такие ситуации возникают при:

- создании эмбеддингов;
- формировании кратких сводок (саммари);
- дедупликации;
- извлечении сущностей;
- агрегации;
- построении графов;
- нормализации представлений;
- создании поисковых индексов;
- извлечении фактов с помощью LLM.

Из этого следует важный вывод:

> **Synanton не должен пытаться восстановить историю происхождения (провенанс) путем математического обращения проекции.**

------

# 8. Провенанс и граф зависимостей

Вместо попыток обращения функции Synanton явно фиксирует процесс получения данных (деривацию).

Например:

```text
Фрагмент X
получен из:
Документ A:v17
Документ B:v4
```

и:

```text
Эмбеддинг E1
получен из:
Фрагмент X:v2
модель-эмбеддинга:v5
```

В результате формируется граф происхождения:

```text
Документ A:v17 ──┐
                 ├──> Фрагмент X:v2 ───> Эмбеддинг E1
Документ B:v4  ──┘
```

Для объекта, сформированного из нескольких источников:

```text
FileNET/doc-991@42 ─────┐
DB1/customer-123@781 ───┼──> BusinessObject@17
DB2/contract-555@154 ───┘
```

Этот граф позволяет Synanton отвечать на такие вопросы, как:

- Что послужило источником этой проекции?
- Какие версии исходных данных участвовали в ее создании?
- Какие проекции зависят от этого источника?
- Что устареет при изменении этого источника?
- Какие права доступа влияют на этот производный объект?
- Почему был получен именно такой результат? - Какое преобразование привело к его появлению?

В этом и заключается роль провенанса.

------

# 9. Контракт формирования проекции (derivation contract)

У проекции должен быть явный контракт формирования.

Концептуально:

```text
ProjectionContract

    sourceRepositories
    projectionRepository
    
    processor
    processorVersion
    
    ontology
    ontologyVersion
    
    configuration
    configurationVersion
    
    dependencySelector
    
    signatureScheme
    
    validationRules
```

Этот контракт определяет условия, при которых проекция считается валидной.

Например:

```text
ProjectionContract:
    source = FileNET
    projection = Lucene
    processor = legal-document-indexer
    processorVersion = 7
    ontologyVersion = 12
```

Затем объект проекции может быть проверен на соответствие этому контракту.

------

# 10. Идентификатор формирования проекции (derivation identity)

Идентификатор проекции не должен сводиться к контрольной сумме физической исходной записи.

Проекция может зависеть лишь от определенных полей источника.

Например:

```text
Запись клиента (Customer record):

customer_id
name
email
last_login
internal_counter
updated_by
```

Если проекция зависит только от:

```text
customer_id
name
email
```

то изменения в полях:

```text
last_login
internal_counter
updated_by
```

не обязательно должны приводить к невалидности проекции.

Таким образом, контракт формирования определяет **семантическую зависимость**.

Подпись проекции отражает состояние, значимое для данного процесса формирования.

Концептуально:

```text
projection_signature =
    H(
        source dependencies,
        source versions,
        ontology version,
        processor version,
        relevant configuration
    )
```

Подпись дает ответ на вопрос:

> **Какое состояние источника и какой контракт формирования породили эту проекцию?**

Это не просто контрольная сумма двух физических записей.

------

# 11. Компонентные и составные сигнатуры

Для проекций, формируемых на основе нескольких источников, полезно использовать два уровня сигнатур.

## 11.1 Компонентные сигнатуры

Каждая зависимость имеет собственную сигнатуру:

```text
FileNET/doc-991@42
    signature = A

DB1/customer-123@781
    signature = B

DB2/contract-555@154
    signature = C
```

## 11.2 Составная сигнатура проекции

Тогда проекция может иметь следующую сигнатуру:

```text
projection_signature =
    H(
        processorVersion,
        ontologyVersion,
        configurationVersion,
        A,
        B,
        C
    )
```

Это обеспечивает два режима работы.

### Быстрая проверка

```text
ожидаемая составная сигнатура
==
фактическая составная сигнатура
```

### Диагностическая проверка

В случае расхождения:

```text
сравнение компонентных сигнатур

FileNET    - OK
DB1        - CHANGED
DB2        - OK
```

Это важно для масштабной проверки согласованности, так как система может определить изменившуюся зависимость без пересчета или сравнения всех исходных объектов.

# 12. Запись о происхождении (Lineage record)

Материализованная проекция должна предоставлять метаданные о своем формировании.

Пример:

```json
{
  "projection": "lucene",
  "objectId": "business-123",

  "dependencies": [
    {
      "repository": "filenet",
      "id": "doc-991",
      "version": 42,
      "signature": "A"
    },
    {
      "repository": "db1",
      "id": "customer-123",
      "version": 781,
      "signature": "B"
    },
    {
      "repository": "db2",
      "id": "contract-555",
      "version": 154,
      "signature": "C"
    }
  ],

  "processor": "business-object",
  "processorVersion": 17,

  "ontologyVersion": 12,

  "signature": "X"
}
```

Эта запись поддерживает:

- проверку согласованности;
- отслеживание происхождения (provenance);
- анализ влияния (impact analysis);
- анализ безопасности; - отладка;
- воспроизводимость;
- инвалидация;
- инкрементальная пересборка.

# 13. Жизненный цикл проекции

У материализованной проекции есть свой жизненный цикл.

```text
    ┌──────────────┐
    │  Построение  │ 
    └──────┬───────┘
           ▼
     ┌────────────┐
     │  Валидна   │
     └─────┬──────┘
           ▼
     изменение источника/
    конфигурации/онтологии
           │
           ▼
    ┌──────────────┐
    │  Устарела    │
    └──────┬───────┘
           ▼
    ┌──────────────┐
    │ Перестроение │
    └──────┬───────┘
           ▼
    ┌────────────┐
    │  Валидна   │
    └────────────┘
```

К числу других терминальных или исключительных состояний могут относиться:

```text
    MISSING           (Отсутствует)
    ORPHAN            (Отсоединенная)
    INVALID           (Невалидна)
    BLOCKED           (Заблокированная)
    SECURITY_INVALID  (Нарушение политики безопасности)
    UNSUPPORTED       (Не поддерживается)
```

Полезно различать состояния **stale** (устаревшая) и **invalid** (невалидная):

- **stale** означает, что проекция была валидной для предыдущего состояния зависимостей, но уже существует более новое ожидаемое состояние;
- **invalid** означает, что проекция не удовлетворяет контракту формирования (derivation contract) даже для того состояния зависимостей, которое она, как предполагается, представляет.

------

# 14. Состояния согласованности

Универсальный механизм проверки согласованности способен выявлять как минимум следующие состояния:

| Состояние          | Значение                                                     |
| ------------------ | ------------------------------------------------------------ |
| `VALID`            | Проекция удовлетворяет контракту формирования              |
| `MISSING`          | Ожидаемая проекция отсутствует                             |
| `ORPHAN`           | Проекция ссылается на недоступное/несуществующее состояние источника |
| `STALE`            | Состояние источника или входные данные формирования обновились |
| `INVALID`          | Сигнатура или содержимое проекции нарушают контракт          |
| `WRONG_PROCESSOR`  | Проекция построена с использованием неожиданной версии процессора |
| `WRONG_ONTOLOGY`   | Проекция построена с использованием несовместимой версии онтологии |
| `SECURITY_INVALID` | Проекция нарушает политику безопасности формирования         |
| `BLOCKED`          | Проекция в данный момент не может быть перестроена или проверена |
| `UNSUPPORTED`      | Система не может определить валидность в рамках имеющегося контракта |

Эту классификацию следует рассматривать как часть жизненного цикла знаний, а не как специфичную для конкретной реализации таксономию ошибок.

------

# 15. Инкрементальная инвалидация

Граф зависимостей делает возможной инкрементальную инвалидацию. Допустим:

```text
DB2@154 -> DB2@155
```

Тогда:

```text
Изменяется сигнатура DB2
        │
        ▼
Изменяется зависимая составная сигнатура
        │
        ▼
BusinessObject становится неактуальным (STALE)
        │
        ▼
Проекция Lucene становится неактуальной (STALE)
```

Объекты, не связанные с данным изменением, пересчитывать не нужно.

Общий процесс выглядит так:

```text
Изменение источника
        │
        ▼
Определение затронутых узлов зависимостей
        │
        ▼
Обход графа производных данных (в направлении от источника)
        │
        ▼
Пометка затронутых проекций как неактуальных
        │
        ▼
Планирование пересчета
        │
        ▼
Материализация новых версий проекций
        │
        ▼
Проверка (валидация)
        │
        ▼
Публикация нового валидного состояния
```

По сути, это аналог инкрементальной компиляции, примененный к данным.

------

# 16. Материализованные проекции образуют граф сборки

Таким образом, архитектуру можно представить следующим образом:

```text
                      Исходное состояние
                              │
                              ▼
                    Контракт преобразования
                              │
               ┌──────────────┼──────────────┐
               ▼              ▼              ▼
          Лексический    Семантический  Структурный
          процессор        процессор      процессор
               │              │              │
               ▼              ▼              ▼
      Инвертированный     Векторное       Графовое
           индекс        хранилище         хранилище
               │              │              │
               └──────────────┼──────────────┘
                              ▼
                         Извлечение
```

Каждый узел - это материализованное представление.

Каждое ребро - это отношение преобразования.

Каждый производный узел сам может стать источником для другой проекции:

```text
Документ
   │
   ▼
Фрагмент
   │
   ▼
Эмбеддинг
   │
   ▼
Векторный индекс
```

Следовательно, вся система представляет собой направленный граф зависимостей, а не линейный конвейер обработки.

------

# 17. Онтология как семантический контракт

Онтология - это нечто большее, чем просто словарь.

Она определяет семантическое пространство, в котором функционируют проекции и запросы.

Например:

```text
Клиент
Контракт
Продукт
Заказ
```

с отношениями:

```text
Клиент ── владеет ──> Контракт
Контракт ── охватывает ──> Продукт
Клиент ── разместил ──> Заказ
```

Онтология может определять:

- сущности;
- отношения;
- релевантные атрибуты;
- семантические эквивалентности;
- концепции предметной области;
- ограничения;
- семантику запросов.

Таким образом, процессор проекции можно представить в виде модели:

```text
Pi = Ti(S, O, C)
```

где:

- `S` = исходное состояние;
- `O` = состояние онтологии;
- `C` = конфигурация процессора;
- `Ti` = версионированный процессор;
- `Pi` = проекция.

------

# 18. Изменения онтологии и валидность проекции

Версию онтологии следует рассматривать как зависимость преобразования, если семантика процессора зависит от нее.

Например:

```text
Документ@42
Онтология@7
Фрагментатор@3
   │
   ▼
Фрагмент@100
```

Если онтология изменяется:

```text
Онтология@7 -> Онтология@8
```

существующий фрагмент не во всех системах автоматически становится невалидным. Вместо этого договор о производности определяет, совместима ли

```text
Ontology@8
```

с существующей проекцией.

Если изменение онтологии затрагивает семантику проекции, проекция считается устаревшей и подлежит перестроению.

Это предпочтительнее, чем исходить из того, что любое изменение версии онтологии неизбежно делает все проекции недействительными.

------

# 19. Множественные проекции одних и тех же знаний

Не существует единственного, универсально верного способа материализации корпоративных знаний.

Различные проекции сохраняют разные свойства.

| Проекция                | Преимущественно сохраняет                    |
|-------------------------|----------------------------------------------|
| Лексическая             | точные термины, идентификаторы, терминологию |
| Семантическая/векторная | семантическую близость                       |
| Структурная             | связи и топологию                            |
| Иерархическая           | контекст документов и разделов               |
| Объектная               | нормализованные сущности и понятия           |
| Временная               | временные связи и применимость               |
| Аналитическая           | агрегаты и производные показатели            |

Следовательно:

```text
Исходные знания
    │
    ├── лексическая проекция
    ├── семантическая проекция
    ├── структурная проекция
    ├── иерархическая проекция
    ├── объектная проекция
    └── аналитическая проекция
```

Эти проекции дополняют друг друга.

------

# 20. Поиск на основе онтологии

Поэтому поиск не должен сводиться к схеме:

```text
Запрос -> Векторная база данных
```

Вместо этого:

```text
                     Запрос
                       │
                       ▼
                 Семантика запроса
                       │
                       ▼
                    Онтология
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
   Лексический   Семантический    Обход
        поиск        поиск        графа
          │            │            │
          └────────────┼────────────┘
                       ▼
                  Объединение
                       │
                       ▼
               Переранжирование
                       │
                       ▼
                     Ответ
```

Онтология задает семантическую систему координат.

Проекции обеспечивают различные физические воплощения этого семантического пространства.

Это приводит к важному разграничению:

> **Онтология определяет смысл знаний; проекции определяют, как эти знания материализуются для вычислений.**

------

# 21. Происхождение и поиск

Результаты поиска должны сохранять связь с данными об их происхождении (провенансом).

В идеале результат должен допускать прослеживаемость по цепочке:

```text
    Запрос
      │
      ▼
    Результат проекции
      │
      ▼
    Объект проекции
      │
      ▼
    Запись о формировании
      │
      ▼
    Версия источника
      │
      ▼
    Артефакт-источник
```

Это обеспечивает:

- проверку обоснованности;
- возможность аудита;
- воспроизводимость;
- авторизацию на уровне источника;
- отладку;
- объяснение производных фактов;
- пересборку и аннулирование (признание неактуальным).

Таким образом, результат поиска без данных о происхождении является менее ценным элементом корпоративных знаний.

------

# 22. Безопасность как свойство производного результата

Безопасность нельзя рассматривать просто как:

```text
ACL источника, скопированный в проекцию
```

поскольку производное знание может раскрывать информацию, которой нет в явном виде в исходном представлении.

Например:

```text
D1 -> У Алисы есть доступ
D2 -> У Боба есть доступ
D3 -> У Кэрол есть доступ

D1 + D2 + D3
    │
    ▼
Выручка = $600 млн
```

Агрегированный результат может раскрывать информацию об исходных объектах с ограниченным доступом, даже если в проекции отсутствует их исходный текст.

Следовательно:

> **Безопасность производного знания не обязательно тождественна безопасности исходных документов.**

Безопасность должна оцениваться с учетом информации, раскрываемой в результате операции вывода (производного представления).

------

# 23. Прямое распространение требований безопасности

Как минимум, архитектура должна обеспечивать прямой поток передачи требований безопасности:

```text
Безопасность источника
    │
    ▼
Политика формирования производного результата
    │
    ▼
Безопасность проекции
```

Соглашение о формировании производного результата определяет, как требования безопасности источника влияют на итоговую проекцию.

Политика может зависеть от:

- классификации источников;
- субъектов доступа (принципалов);
- арендаторов (тенентов);
- рабочих задач (дел/проектов);
- сегментов доступа (compartments);
- этических барьеров (ethical walls);
- семантики агрегирования;
- семантики проекции.

Конкретный вид политики зависит от предметной области.

------

# 24. Анализ обратного влияния на безопасность

Граф происхождения данных (provenance graph) позволяет задать обратный вопрос:

```text
Проекция
    │
    ▼
Какие источники участвовали в формировании? 
    │
    ▼
Какие политики безопасности применяются?
```

Например:

```text
Проекция P
    │
    ├── Документ A
    ├── Документ B
    └── Запись в БД C
```

Если права доступа к `Документу B` изменяются, система может выявить зависящие от него проекции.

Это обеспечивает следующий процесс:

```text
изменение требований безопасности
    │
    ▼
анализ влияния
    │
    ▼
признание проекции недействительной
    │
    ▼
пересоздание или обновление политики доступа
```

Таким образом, обратная операция представляет собой **анализ влияния**, а не обратную проекцию.

------

# 25. Решетки безопасности

В сложных системах безопасность можно моделировать как упорядоченное пространство политик.

Концептуально:

```text
S1 ⊑ S2
```

где отношение порядка отражает определенную связь между информацией, разрешенной данными политиками.

Процесс вывода (derivation) должен удовлетворять ограничению безопасности, например:

```text
Security(P)
    ⊑
AllowedSecurity(Derivation(P))
```

Конкретный вид решетки и отношения порядка зависят от особенностей реализации системы.

Важный архитектурный принцип:

> **Политика безопасности влияет на корректность вывода.**

Это связывает материализованные проекции со следующими аспектами:

- контроль потоков информации;
- отслеживание «загрязненных» данных (taint tracking);
- распространение правил контроля доступа;
- вычисления с учетом политик безопасности.

------

# 26. Временная семантика и семантика версий

Идентификатор версии является зависимостью проекции первого класса.

Проекция должна указывать точную версию источника, на основе которой она была получена:

```text
Document@42
    │
    ▼
Chunk@17
```

а не просто:

```text
Document 123
```

Это важно, поскольку корпоративные знания со временем меняются.

Историческая проекция может оставаться валидной для:

```text
Document@42
```

даже после того, как:

```text
Document@43
```

станет текущей версией.

Следовательно:

> **Текущее состояние источника и валидность исторической проекции - это разные понятия.**

Граф вывода должен сохранять ссылки на версии, необходимые для определения того, какому состоянию знаний соответствует проекция.

Для временных доменов в семантике проекции могут также участвовать дополнительные временные метаданные, если процессор зависит от них.

------

# 27. Воспроизводимость

Проекция должна быть воспроизводимой на основе объявленных зависимостей.

Концептуально:

```text
Projection =
    F(
        версии источников,
        версия онтологии,
        версия процессора,
        конфигурация
    )
```

Это обеспечивает более надежные гарантии, чем просто хранение метки:

```text
created_at
```

Система должна уметь объяснить:

```text
Почему существует эта проекция?
```

следующим образом:

```text
потому что были использованы:
источник A@42,
источник B@17,
онтология@8,
процессор@12,
конфигурация@4.
```

------

# 28. Идентификация материализованной проекции

Полезно различать следующие понятия:

### Идентификатор источника

```text
(репозиторий, ID объекта, версия)
```

### Идентификатор процесса преобразования (деривации)

```text
(процессор, версия процессора,
версия онтологии,
версия конфигурации)
```

### Идентификатор проекции

```text
(репозиторий проекции,
ID объекта проекции,
версия проекции)
```

### Идентификатор зависимости

```text
(идентификатор источника + подпись источника)
```

### Валидность проекции

```text
валидность =
    зависимости от источников
    +
    контракт преобразования
    +
    политика безопасности
    +
    подпись проекции
```

Такое разделение позволяет избежать распространенной ошибки, когда идентификатор объекта ошибочно принимается за исчерпывающее описание истории происхождения (lineage).

------

# 29. Проверка согласованности

Универсальный механизм проверки согласованности работает с графом зависимостей.

Минимальный набор выполняемых им операций:

```text
scan()                      // сканирование
fetch()                     // получение данных
resolveDependencies()       // разрешение зависимостей
computeExpectedSignature()  // вычисление ожидаемой подписи
compare()                   // сравнение
classify()                  // классификация результата
```

Механизму проверки не нужно знать внутреннее устройство каждого конкретного физического репозитория.

Ему необходимы:

```text
Контракт репозитория
    +
Контракт преобразования
    +
Метаданные о происхождении (provenance)
```

Благодаря этому проверка согласованности не зависит от конкретной реализации репозитория.

------

# 30. Быстрая и диагностическая проверка

Процесс проверки согласованности должен поддерживать два сценария выполнения.

## Быстрый сценарий

```text
ожидаемая подпись  ==  фактическая подпись
```

Результат:

```text
ВАЛИДНО
```

или:

```text
НЕВАЛИДНО
```

## Диагностический сценарий

Если подписи различаются:

```text
проекция
    ↓
набор зависимостей
    ↓
подписи компонентов
    ↓
выявление измененной зависимости
```

Пример:

```text
FileNET   -> без изменений
DB1       -> изменено
DB2       -> без изменений
Процессор -> без изменений
Онтология -> без изменений
```

Это позволяет крупномасштабным системам выполнять обычную проверку с минимальными затратами ресурсов, сохраняя при этом возможность получения детальной диагностики при необходимости.

------

# 31. Аналогия с системой сборки

Данная архитектура имеет тесную аналогию с системой инкрементальной сборки программного обеспечения.

| Система сборки           | Система проекции знаний         |
|--------------------------|---------------------------------|
| исходный файл            | исходный артефакт               |
| версия исходного кода    | версия источника                |
| компилятор               | процессор проекции              |
| версия компилятора       | версия процессора               |
| конфигурация сборки      | конфигурация вывода             |
| скомпилированный объект  | материализованная проекция      |
| граф зависимостей        | граф происхождения (provenance) |
| хеш артефакта сборки     | подпись проекции                |
| устаревший объект        | устаревшая проекция             |
| инкрементальная сборка   | инкрементальное пересоздание    |
| кэш компилятора          | кэш проекций                    |
| проверка сборки          | проверка согласованности        |

Изменение источника:

```text
source.java@42 -> source.java@43
```

может сделать:

```text
class@42
jar@42
```

устаревшими.

Аналогично:

```text
Document@42 -> Document@43
```

может сделать:

```text
Chunk@17
Embedding@22
IndexEntry@91
GraphFact@12
```

устаревшими.

Это дает Synanton полезную концептуальную модель:

> **Synanton - это система инкрементальной сборки для корпоративных знаний.**

------

# 32. Аннулирование - это операция первого класса

Аннулирование не должно быть случайным побочным эффектом пересоздания.

Это должна быть явная операция жизненного цикла.

```text
изменение источника
     ↓
обход графа зависимостей
     ↓
затронутые проекции
     ↓
пометка как устаревших
     ↓
пересоздание
     ↓
проверка
     ↓
публикация
```

Это обеспечивает:

- ограниченный объем пересоздания;
- предсказуемое поведение системы;
- планирование с учетом зависимостей;
- обработку частичных сбоев;
- наблюдаемость;
- оценку затрат.

------

# 33. Возможность пересоздания

Важнейшим свойством материализованной проекции является **возможность пересоздания**.

Если проекция утеряна:

```text
Репозиторий проекций недоступен
```

система должна иметь возможность восстановить ее на основе:

```text
версий источников
  +
контракта вывода
  +
онтологии
  +
конфигурации
```

при условии доступности необходимых исходных артефактов. Это одно из основных различий между:

```text
производным знанием
```

и:

```text
независимыми авторитетными данными.
```

Проекция в принципе является одноразовой, даже если её повторное создание обходится дорого.

------

# 34. Качество проекции

Не каждая проекция сохраняет один и тот же набор информации.

Поэтому при оценке проекции следует измерять, насколько хорошо она сохраняет свойства, необходимые для выполнения целевой рабочей нагрузки.

Для проекций, ориентированных на поиск информации, к числу значимых метрик относятся:

- Recall@K (полнота на топ-K);
- Precision (точность);
- MRR (средний обратный ранг);
- NDCG@K (нормированный дисконтированный кумулятивный выигрыш на топ-K);
- качество обоснования (evidence quality);
- качество ответа;
- задержка (latency) на уровне перцентилей p50/p95/p99;
- утечка конфиденциальных данных (security leakage);
- полнота данных о происхождении (provenance completeness);
- стоимость инвалидации;
- стоимость перестроения.

Различные проекции оптимизируют разные целевые показатели.

Следовательно:

> **Качество проекции зависит от рабочей нагрузки.**

Векторная проекция может оптимизировать семантическое сходство.

Лексическая проекция может оптимизировать точность терминологии.

Графовая проекция может оптимизировать обход связей.

Иерархическая проекция может оптимизировать контекстный поиск.

Архитектура должна допускать сосуществование этих представлений.

# 35. Объединение проекций (Fusion)

В рамках одного запроса могут использоваться несколько проекций.

Например:

```text
Запрос
│
▼
Онтология
│
┌────────────┼────────────┐
▼            ▼            ▼
Лексическая    Семантическая   Графовая
│            │            │
└────────────┼────────────┘
▼
Объединение
│
▼
Переранжирование
│
▼
Обоснование
│
▼
Ответ
```

Проекции не являются конкурирующими источниками истины.

Они представляют собой взаимодополняющие пути доступа к единому, управляемому состоянию знаний. ------

# 37. Что означает понятие «корпоративные знания» в данной модели

Таким образом, корпоративные знания - это не просто:

> набор документов.

И не просто:

> граф знаний.

И не просто:

> векторная база данных.

Более точное определение:

> **Корпоративные знания - это набор семантических проекций, созданных на основе разнородных исходных хранилищ; они имеют версионирование, отслеживаемую историю происхождения (провенанс) и ограничения доступа, управляются явными правилами формирования (контрактами вывода) и доступны для запросов через онтологию.**

Это определение объясняет, почему для работы с корпоративными знаниями требуется более развитая инфраструктура, чем для стандартного конвейера RAG (Retrieval-Augmented Generation).

------

# 38. Что обеспечивает Synanton

В рамках этой модели Synanton отвечает за жизненный цикл производных знаний:

```text
 загрузка (ingest)
    ↓
 нормализация
    ↓
 версионирование
    ↓
 интерпретация
    ↓
 проецирование
    ↓
 материализация
    ↓
 обеспечение безопасности
    ↓
 индексация
    ↓
 запрос
    ↓
 вывод (derivation)
    ↓
 проверка (валидация)
    ↓
 инвалидация
    ↓
 пересборка
```

Ключевые механизмы:

```text
Версии источников
    +
Контракты вывода
    +
Материализованные проекции
    +
Граф происхождения (провенанс)
    +
Политика безопасности
    +
Проверка согласованности
    +
Инкрементальное аннулирование
```

В совокупности они обеспечивают управляемый жизненный цикл корпоративных знаний.

# 39. Архитектурные принципы

Модель можно свести к следующим принципам.

### Принцип 1 - Источники остаются авторитетными

Материализованные проекции - это производное состояние, а не независимые источники истины.

### Принцип 2 - Проекции явны

Каждое производное представление должно иметь четко определенный контракт проекции.

### Принцип 3 - Вывод осуществляется по принципу «многие-ко-многим»

Проекция может зависеть от нескольких исходных артефактов, а один источник может порождать множество проекций.

### Принцип 4 - Проекции, как правило, необратимы

Система не должна полагаться на восстановление исходного состояния на основе проекции.

### Принцип 5 - Провенанс (история происхождения) явен

Зависимости фиксируются явно, а не выводятся из содержимого проекции.

### Принцип 6 - Версии являются зависимостями

Проекция указывает версии источников, на основе которых она была создана.

### Принцип 7 - Процесс вывода воспроизводим

Процессор, онтология, конфигурация и зависимости, необходимые для воспроизведения проекции, определены явно. ### Принцип 8 - Валидность определяется контрактом

Проекция считается валидной, если она удовлетворяет контракту, определяющему правила ее формирования.

### Принцип 9 - Безопасность влияет на валидность

Проекция, нарушающая политику безопасности, регламентирующую ее формирование, не является валидной.

### Принцип 10 - Невалидность распространяется по цепочке зависимостей

Изменения в исходных данных распространяются по графу происхождения (провенанса), не требуя глобального пересчета.

### Принцип 11 - Проекции дополняют друг друга

Различные проекции сохраняют разные свойства и могут использоваться совместно в одной операции извлечения данных.

### Принцип 12 - При извлечении данных сохраняется информация о происхождении

Извлеченные знания должны позволять проследить связь с соответствующей материализованной проекцией и авторитетными версиями исходных данных.

# 40. Итоговая модель

Полную модель можно представить следующим образом:

```text
        ИСТОЧНИК ЗНАНИЙ
                │
                ▼
        ВЕРСИОНИРОВАННЫЕ ИСТОЧНИКИ
                │
                ▼
        КОНТРАКТЫ ПРЕОБРАЗОВАНИЯ
                │
                ├── процессор
                ├── онтология
                ├── конфигурация
                └── политика безопасности
                │
                ▼
      МАТЕРИАЛИЗОВАННЫЕ ПРОЕКЦИИ
                │
      ┌─────────┼─────────┐
      ▼         ▼         ▼
  лексическая семантическая структурная
      │         │         │
      ▼         ▼         ▼
    индекс    векторы     граф
      │         │         │
      └─────────┼─────────┘
                ▼
              ПОИСК
                │
                ▼
            ОБОСНОВАНИЕ
                │
                ▼
            РАССУЖДЕНИЕ

┌───────────────────────────────────────┐
│                                       │
│           ГРАФ ПРОИСХОЖДЕНИЯ          │
│                                       │
│  версии · зависимости · подписи       │
│  безопасность · валидность · история  │
│                                       │
└───────────────────────────────────────┘
                 │
    ┌────────────┼────────────┐
    ▼            ▼            ▼
проверка     аннулирование  пересборка
```

Таким образом, фундаментальной абстракцией является не:

```text
Документ -> RAG
```

а:

```text
    Состояние авторитетного источника
        │
        ▼
    Версионированное преобразование
        │
        ▼
    Материализованная проекция
        │
        ▼
    Происхождение + Безопасность + Валидность
        │
        ▼
    Поиск / Рассуждение
```

А основной операционный цикл выглядит так:

```text
    ИЗМЕНЕНИЕ ИСТОЧНИКА
        │
        ▼
    АНАЛИЗ ВЛИЯНИЯ
        │
        ▼
    АННУЛИРОВАНИЕ
        │
        ▼
    ИНКРЕМЕНТАЛЬНАЯ ПЕРЕСБОРКА
        │
        ▼
    ПРОВЕРКА СОГЛАСОВАННОСТИ
        │
        ▼
    НОВОЕ СОСТОЯНИЕ МАТЕРИАЛИЗОВАННОГО ЗНАНИЯ
```

Это архитектурная основа для работы со знаниями предприятия как с управляемой, пересобираемой и аудируемой системой производных представлений, а не как с набором независимо управляемых индексов.

> **Synanton — это движок проекции знаний: он создает, поддерживает, проверяет, защищает, ищет, аннулирует и пересобирает материализованные проекции знаний предприятия.**
